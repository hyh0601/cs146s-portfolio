**b. 语气与啰嗦程度。**（原文：`system` 第 3 张卡第 52 行）
```
When you have enough information to act, act. Do not re-derive facts already
established in the conversation, re-litigate a decision the user has already
made, or narrate options you will not pursue. If you are weighing a choice,
give a recommendation, not an exhaustive survey.
```
> 防三种毛病：
>
> ① 信息够了还不动手；
> ② 把已经说清的事重新推一遍、把已经拍板的决定翻出来再议；
> ③ 列一堆选项不给建议（应该直接说"我建议做 A"）。
>
> 本质：**防"话多但不往前推"**，防止把三分钟能干的活聊成半小时。

**c. 什么时候不该动手。**（原文：`system` 第 3 张卡第 15 行 + 第 8 行）
```
For actions that are hard to reverse or outward-facing, confirm first unless
durably authorized or explicitly told to proceed without asking; approval in
one context doesn't extend to the next. Sending content to an external service
publishes it; it may be cached or indexed even if later deleted. Before deleting
or overwriting, look at the target. Report outcomes faithfully: if tests fail,
say so with the output; if a step was skipped, say that; when something is done
and verified, state it plainly without hedging.
```
```
 - Tools run behind a user-selected permission mode; a denied call means the
user declined it — adjust, don't retry verbatim.
```
> 这段在管四件事：
>
> ① **不可逆或对外的操作，先问再动手**：删除、覆盖、发到外部服务之前先确认，
>    一次授权只管一次——上次同意不等于这次同意。
> ② **发出去的东西等于发布了**：可能已被缓存、被索引，就算之后删掉也收不回来。
> ③ **删或覆盖之前先看 target**：target 就是"要删/覆盖的那个东西本身"（文件、目录、整个工作区），
>    先打开看一眼，确认删的不是别的文件。
> ④ **结果要如实说**：测试没过就带着输出说出来，跳过了哪步就说跳过了，做完了才说做完了。
>    防的是"报喜不报忧"——把失败包装成"基本完成"。
>
> 一句话：防"做了收不回来、事后还不认账"的操作。

**挑两个工具。** 选彼此差异大的两个。

| | 工具 1 | 工具 2 |
|---|---|---|
| 名字 | `AskUserQuestion`（向你求裁决） | `Edit`（自己动手改文件） |
| 关键 schema 字段 | `questions`（数组，1–4 个问题，每个带 options）、`answers`、`annotations`、`metadata`；必填只有 `questions` | `file_path`、`old_string`、`new_string`、`replace_all`；前三个必填 |
| 必填 vs 可选 vs 不暴露，以及为什么 | `answers` / `annotations` 虽然出现在 schema 里，但它们是**客户端的权限组件回填的**，模型不该自己填；不暴露"自由追问"参数，用户只能从预设选项里选或选 Other | `replace_all` 可选（默认 false）；**不暴露**正则、多文件批量、"插入一行"这种参数——工具刻意只做"精确替换一处或全部" |
| 描述在防什么（引用原文 + 它想避免的错误行为） | `Use this tool only when you are blocked on a decision that is genuinely the user's to make`——防"什么事都弹窗问你"；`Do NOT use this tool to ask "Is my plan ready?"`——防拿它当确认按钮 | `You must Read the file in this conversation before editing, or the call will fail`——防**没看过就盲改**；`old_string must match the file exactly... and be unique`——防**改错位置**（同一个词出现多次时），这是盲改最常见的翻车方式 |

为什么选这两个？
> 它们代表 agent 的两类核心动作：**向你求裁决**（`AskUserQuestion`）和**自己动手**（`Edit`）。
> 一个管"人"，一个管"文件"，schema 的取舍方向完全不同——正好用来看"工具设计怎么塑造行为"。

## Part V：反思

**你会照抄的两个决策**，各自解决什么问题：
1. **拿不准的地方用 `AskUserQuestion` 问人，而不是自己猜。** 这次它问的是"空后缀算严格还是宽松"——
   这个问题它读代码也定不了，猜错就得返工。解决的是"替用户做决定"的风险。
2. **计划里主动写出"可能出问题的地方"。** 它列了"允许几段""`parse_version` 报错信息会变"
   这类假设和副作用。解决的是"计划看着漂亮、实际藏着坑"。

**你会做得不一样的一个**（先想清楚它可能是为了防什么）：
> 暂时想不出更好的做法——它这次想得比我自己动手时全面（先读全项目、先问再改、改完跑全量）。
> 唯一想加的一条：**要求它先写测试再写实现**，而不是实现完再补测试。现在的顺序能过，
> 但那是因为我事先埋了红灯；如果任务换成一个我想不清楚的，先写测试能逼它先把需求说清楚。

**这次 trace 改变了你指挥 coding agent 的哪一点**：
> 以后给的指令**约束会更多**。看完抓包才意识到 agent 能做的事太多——它能上传文件、能用
> `git add -f` 绕过 `.gitignore` 把密钥提交上去、能读任何它想读的文件。
> 这些都不是它"坏"，是能力本身。所以要在指令层面收紧：明确不许做什么、哪些操作必须先问、
> 什么文件不许碰。
